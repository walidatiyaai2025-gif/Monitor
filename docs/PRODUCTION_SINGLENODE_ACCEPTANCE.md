# P0.5 — First Production SingleNode Acceptance

Issue: #116  
Dependency: P0.4 / #115 COMPLETE  
Scope: first production activation only; `Deployment:Mode=SingleNode`.

This document is the operator evidence record for the first IIS/HTTPS production cutover. Repository CI can prove the package, configuration contracts and deterministic recovery behavior, but it cannot truthfully close #116 without exercising the actual Windows/IIS environment.

## Release candidate contract

1. Use the versioned Windows x64 ZIP and matching `.sha256` generated by `.github/workflows/release.yml`.
2. Verify the SHA-256 before extracting or deploying.
3. Keep `deploy/appsettings.Production.example.json` as a schema/example only; do not place real secrets in source-controlled JSON.
4. Set `Deployment:Mode=SingleNode`. MultiNode is explicitly out of scope for P0.5.
5. Persist the application state directory and ASP.NET Data Protection key ring outside the replaceable release folder.
6. Use the existing monitored-SQL least-privilege role; the application must not require write access to monitored SQL targets.
7. Bind IIS to HTTPS. HTTP is not accepted as production evidence.

## Deployment procedure

1. Run the normal Release build/tests and obtain the release artifact from the `release` workflow.
2. Verify artifact SHA-256.
3. Create an operational backup and preserve the previous release as the rollback point.
4. Stop/recycle only the Monitor IIS application pool required for the deployment.
5. Deploy the new application files without deleting durable state or Data Protection keys.
6. Apply production configuration through approved environment/configuration sources; do not copy credential values into this evidence file.
7. Start/recycle the app pool and verify IIS HTTPS binding/certificate.
8. Run:

```powershell
./scripts/Accept-ProductionSingleNode.ps1 `
  -BaseUri https://monitor.example.internal/ `
  -ArtifactPath .\Monitor-<version>-win-x64.zip `
  -ChecksumPath .\Monitor-<version>-win-x64.zip.sha256 `
  -EvidencePath .\evidence\p0-5-singlenode.json
```

The script validates the artifact checksum and the three control-plane health endpoints. It intentionally leaves restart, credential, SQL privilege, backup and rollback operator checks false until those are manually proven.

## Mandatory restart/recycle acceptance

After the first Green health smoke:

1. Confirm at least one real SQL registration is visible from persisted application state.
2. Record its opaque registration id only; never record a password or current secret value.
3. Recycle the IIS application pool.
4. Confirm `/health/live`, `/health/ready`, and `/health` return the expected bounded statuses again.
5. Confirm the same registration id remains present after restart.
6. Execute the approved Test Connection / bounded refresh path and confirm the protected credential resolves after restart.
7. Confirm the Server Details page returns cached/collected evidence without fallback demo data.

Do not cut over, or rollback immediately, if readiness is not Green, the checksum does not match, the application starts in an unintended MultiNode mode, the key ring/state paths are unavailable, protected credentials cannot resolve after recycle, monitored SQL requires unexpected write/high privilege, or rollback/backup evidence is missing.
