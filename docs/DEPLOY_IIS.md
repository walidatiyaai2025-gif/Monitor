# Deploy Monitor on IIS

This is the preferred Windows deployment path for a single Monitor node behind IIS.

## Prerequisites

- Windows Server with IIS.
- .NET 8 ASP.NET Core Hosting Bundle installed on the server.
- A dedicated low-privilege domain or local service identity for the Monitor application pool.
- HTTPS certificate installed in the machine certificate store.
- Published Monitor output produced from a CI-verified commit.

## Publish

```powershell
dotnet restore .\Monitor.sln
dotnet test .\Monitor.sln -c Release --no-restore
dotnet publish .\src\Monitor.Web\Monitor.Web.csproj -c Release -o C:\Deploy\Monitor\candidate
```

Do not copy source-controlled `appsettings.json` into production unchanged. Start from `deploy/appsettings.Production.example.json`, place the resulting `appsettings.Production.json` next to the published application, and keep all secrets in machine/service environment variables.

## IIS site and application pool

1. Create a dedicated application pool, for example `Monitor`.
2. Set **.NET CLR Version** to **No Managed Code**.
3. Use a dedicated service identity; do not run as LocalSystem or an interactive administrator.
4. Grant that identity Modify only on Monitor-owned runtime folders that require writes (`App_Data` when local stores are enabled). Grant Read/Execute on the rest of the deployment directory.
5. Create an IIS site pointing to the publish directory.
6. Bind HTTPS to the production host name and certificate. Do not expose an HTTP-only production binding.
7. Restrict network access to the intended operator networks and SQL endpoints.

The ASP.NET Core Module generated by `dotnet publish` starts the application. Keep the generated `web.config`; do not replace it with a hand-authored process command.

## Required configuration

Set production values through environment variables or `appsettings.Production.json`. Sensitive values must use environment variables.

Common environment variables:

```text
ASPNETCORE_ENVIRONMENT=Production
DevelopmentAdmin__Username=<operator-admin-name>
DevelopmentAdmin__Iterations=<approved-pbkdf2-iteration-count>
DevelopmentAdmin__SaltBase64=<generated-salt>
DevelopmentAdmin__HashBase64=<generated-hash>
MONITOR_SHARED_STATE_SQL_CONNECTION=<dedicated-monitor-state-db-connection-string>
MONITOR_DP_KEK=<base64-encoded-256-bit-key-when-shared-key-ring-is-enabled>
MONITOR_NODE_ID=<stable-opaque-node-id-when-coordination-is-enabled>
```

Only set the shared-state connection and KEK when the corresponding features are enabled. Never place those values in Git, `web.config`, deployment logs or command history.

## Reverse-proxy trust

IIS/ANCM normally supplies the original scheme to ASP.NET Core without requiring Monitor to trust arbitrary `X-Forwarded-*` headers. If another proxy/load balancer is placed in front of IIS or Monitor, configure only its explicit IP/CIDR under `WebSecurity:TrustedProxies` / `TrustedNetworks`. Empty arrays intentionally disable forwarded-header processing.

## First-start verification

From an authorized management host:

```powershell
.\scripts\Smoke-Monitor.ps1 -BaseUri https://monitor.example.internal
```

The smoke test checks process liveness, deployment readiness and the aggregate health endpoint. It does not connect directly to a monitored SQL target.

Then verify:

- `/login` renders over HTTPS.
- Authentication cookie is Secure/HttpOnly/SameSite Strict.
- `/health/live` is healthy.
- `/health/ready` is healthy before admitting normal operator traffic.
- Administrator Settings reports expected topology/shared-state/credential/backup readiness.
- One explicitly configured SQL target passes **Test Connection** before enabling scheduled collection.

## Upgrade

Use `docs/UPGRADE_CHECKLIST.md`. Keep the previous publish directory intact until the new candidate passes smoke tests. On failure, follow `docs/ROLLBACK_RUNBOOK.md` rather than modifying production files in place.
