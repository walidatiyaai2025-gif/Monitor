# B800-093 — no-fake-data environment hardening

## Objective

Continue B800-091..100 final acceptance by closing the remaining production safety gap around the existing Development demo estate. Preserve explicit demo data for local Development while making it impossible to enable synthetic estate data accidentally in Staging, Production or any other non-Development environment.

## Existing behavior and gap

Monitor intentionally retains `DemoMonitorService` for Development. Default `appsettings.json` sets `DemoData:Enabled=false`, while `appsettings.Development.json` opts in with `true`. `MonitorReadService` can use the demo service when there are no enabled registrations or a demo-style non-GUID server ID is requested; with demo disabled that service already returns empty/null rather than synthetic rows.

The gap is configuration hardening: before B800-093, an operator/deployment override could set `DemoData:Enabled=true` outside Development and activate synthetic estate data in a deployed environment. There was no startup guard preventing that misconfiguration.

## Scope

- Add `DemoDataEnvironmentGuard.Validate(IHostEnvironment, IConfiguration)`.
- Permit enabled demo data only when `environment.IsDevelopment()` is true.
- Fail startup when `DemoData:Enabled=true` in Production, Staging or any other non-Development environment.
- Keep `DemoData:Enabled=false` valid in every environment.
- Keep the existing Development demo implementation and DI registration; do not remove the local developer experience.
- Invoke the guard during startup before the demo service registration can be resolved.
- Add acceptance coverage proving:
  - Production/Staging/other non-Development environments reject enabled demo data;
  - Development explicitly permits it;
  - disabled demo configuration returns no synthetic servers/incidents/details;
  - default config remains false and Development config remains explicit true;
  - the startup hook is present before demo-service registration;
  - the guard has no SQL collector/query/refresh/registration dependency.

## Safety boundary

- One startup configuration guard plus tests/documentation.
- No monitored-SQL query, collector, permission or snapshot semantics change.
- No registration mutation, credential write, remediation, tuning, failover, maintenance or backup/restore behavior change.
- No removal of Development-only sample data.
- No RC.61 publication/selection change and no implication for `#162 -> #116 -> #111` production acceptance.
