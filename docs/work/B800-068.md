# B800-068 — Privacy-safe query-regression evidence contract

**Umbrella:** #287  
**State:** IMPLEMENTED / VALIDATION PENDING

## Decision

A privacy-safe query-regression contract is feasible without collecting SQL text, plan XML, session/login/client identity, object names, table data, `sql_handle` or `plan_handle`.

The B400 regression helper must be fed **interval metrics**, not two raw cumulative DMV snapshots.

## Safe cumulative evidence shape

A future bounded collector may retain only:

- SQL Server `query_hash` as an opaque 8-byte/16-hex grouping key;
- optional SQL Server `query_plan_hash` as an opaque 8-byte/16-hex plan-family key;
- an opaque compile/cache epoch derived from the cached-plan compile instance;
- `plan_generation_num`;
- cumulative `execution_count`;
- cumulative `total_elapsed_time`;
- cumulative `total_worker_time`;
- cumulative `total_logical_reads`.

The collector must not cross-apply `sys.dm_exec_sql_text` or any query-plan function.

## Interval rule

`QueryRegressionEvidenceContract.Evaluate` returns a B400 `QueryMetric` only when:

1. both samples contain the same valid query hash;
2. compile/cache epoch is unchanged;
3. plan generation is unchanged;
4. optional plan hash is unchanged within the interval;
5. execution/elapsed/worker/read counters are monotonic;
6. at least one completed execution occurred between samples.

The resulting duration, CPU and logical-read values are per-execution averages of **counter deltas for that interval**. `Executions` is the interval execution delta.

## Fail-closed states

No metric is produced for:

- invalid/oversized hash evidence;
- different query hashes;
- recompile or cache-epoch change;
- plan-hash change inside one interval;
- counters moving backwards after eviction/reset/recompile;
- intervals with no completed executions.

A new stable interval must be established after any cache/generation/plan reset. Missing top-N rows or cache eviction is baseline loss, not evidence of improvement or regression.

## Plan-change handling

A plan change can be compared only **between two separately valid stable intervals**. This allows B400's existing `PlanChanged` logic to compare opaque plan hashes without crossing cumulative-counter reset boundaries.

## Collection intentionally deferred

B800-068 does not add a live query-stats collector, history persistence, UI, alerting or regression score. Before collection is enabled, a follow-up must define:

- bounded ranking and top-N churn behavior;
- compile-epoch projection that detects cache replacement without persisting plan/sql handles;
- snapshot/history retention needed to form two stable intervals;
- stale/unavailable projection and drill-down behavior;
- Real SQL acceptance for reset/eviction behavior where practical.

## Privacy and safety

- no SQL text or sample statement text;
- no query plan/XML;
- no SQL/plan handles persisted;
- no database/table/object names;
- no login/session/client identity;
- no query execution or remediation action;
- no browser-to-SQL path;
- no RC.61 or `#162 -> #116 -> #111` change.

## Validation

Required before merge:

- CI Green on the exact final head;
- Windows production-candidate Green on the exact final head;

Real SQL is not a required gate for this contract-only slice because it adds no SQL query/collector; future live collection must add Real SQL coverage and path selection.
