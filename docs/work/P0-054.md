# P0-054 — Clean IIS start without implicit demo data

**Issue:** #285  
**State:** IN VALIDATION  
**Safety boundary:** repository/staging only; no RC.61 publication, real production IIS/SQL mutation, or #116 acceptance mutation.

## Problem

The read model intentionally fell back to `DemoMonitorService` when no enabled SQL registrations existed. The fallback made a newly installed IIS instance display `DA-SQL01` through `DA-SQL04` and sample incidents even when the persistent `App_Data` state was empty. Deleting `App_Data` therefore could not produce a truthful empty estate.

## Implementation

- `DemoData:Enabled` is now explicit configuration.
- `appsettings.json` and the production example default it to `false`.
- `appsettings.Development.json` opts into the sample estate for local development.
- when disabled, `DemoMonitorService` returns no sample servers/incidents/details and provides a truthful zero-registration dashboard state;
- real registered SQL targets and cached snapshot mapping are unchanged;
- targeted regression tests cover demo-disabled empty estate and explicit demo-enabled behavior.

## Clean staging reset

For a disposable/staging IIS instance only, stop the Monitor site/app pool, back up the existing state if required, then remove the local `App_Data` directory before recreating it and restoring the app-pool ACL. This intentionally removes registrations, protected connection secrets, local Data Protection keys, incidents/audit/history and local operational backups. It must not be used as a production migration procedure.

After restart with `DemoData:Enabled=false`, the estate is empty until an operator adds and tests a real SQL Server in Connection Lab.
