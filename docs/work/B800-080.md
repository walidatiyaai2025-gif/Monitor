# B800-080 — Full Bounded Fleet Correlation Coverage

**Umbrella:** #287  
**State:** canonical reconciliation complete; exact reconciled-head validation pending  
**Scope:** read-only Fleet correlation decision support only.

## Objective

Close the remaining Fleet correlation coverage gap in the B800-071..080 tranche without changing the B400 correlation algorithm or adding monitored-SQL evidence.

Before B800-080, `Batch400FleetCorrelation.Correlate(...)` consumed the Fleet incident signals but the visible Fleet surface requested only `MaxItems = 20` clusters. The table was truthfully bounded, but there was no aggregate showing the complete cluster distribution for the current bounded Fleet decision population.

B800-080 keeps the visible cluster table bounded to 20 rows while computing an aggregate from every B400 cluster that can exist inside the current Fleet decision population.

## B400 bound

`Batch400FleetCorrelation` already clamps `limit` to 100. B800-080 names that existing bound as `MaxClusterLimit = 100`; the algorithm and threshold behavior are unchanged.

The normal Fleet decision path is already bounded to 100 active incidents by `BoundedIncidentReadModel.DefaultLimit`, so a complete Fleet decision population can produce at most 100 correlation clusters. Therefore requesting up to `MaxClusterLimit` clusters is complete for the current runtime Fleet contract.

If `FleetDecisionSupport.Build(...)` is ever supplied more than 100 valid incidents directly, `CorrelationSummary` is `null`. The existing deterministic top-20 correlation detail remains available, but the UI explicitly states that full correlation coverage is not evaluated. This avoids silently extending the B400 contract or claiming a complete aggregate from a truncated cluster set.

## Runtime behavior

For a supported complete bounded population, `FleetDecisionSupport.Build(...)`:

1. preserves the existing valid-incident filter and deterministic incident order;
2. projects the same existing B400 `FleetSignal` inputs;
3. calls `Batch400FleetCorrelation.Correlate(...)` with the existing B400 maximum cluster limit;
4. derives a read-only `FleetCorrelationSummary` containing:
   - evaluated incident count;
   - total cluster count;
   - Critical cluster count;
   - Warning cluster count;
   - Info cluster count;
   - multi-server cluster count;
   - maximum affected-server count observed in a cluster;
   - highest B400 cluster score;
5. retains only the first `FleetDecisionSupport.MaxItems` clusters for row-level display.

No new score, severity threshold, bucketing rule, rule normalization, blast-radius calculation or environment logic is introduced.

## UI behavior

The existing **CORRELATION · DECISION SUPPORT** panel now shows the full bounded correlation coverage before the top-20 table.

The UI explicitly distinguishes:

- aggregate coverage across all incidents admitted by the complete bounded Fleet decision population;
- deterministic top-20 cluster detail.

If a direct caller exceeds the B400 correlation coverage bound, the aggregate is withheld and a warning states that full correlation coverage is not evaluated; top-20 detail remains visible without implying completeness.

## Regression coverage

Coverage locks:

- the B400 cluster limit remains exactly 100 and is named rather than duplicated as a magic number;
- two same-rule/environment/window incidents across two servers form one Critical multi-server cluster and the summary reports blast radius 2;
- 35 unique clusters produce `TotalClusters = 35` while visible correlation detail remains exactly 20;
- a direct 101-incident input withholds `CorrelationSummary` while retaining top-20 detail;
- invalid incident identities are excluded before both routing and correlation summaries;
- existing routing-summary and opaque dedup-key behavior remains intact;
- the UI distinguishes full bounded aggregate coverage from top-20 cluster detail and explicitly fails correlation coverage when outside the B400 bound;
- the surface remains non-executing decision support.
