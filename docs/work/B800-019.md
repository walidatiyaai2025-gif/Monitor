## Decision

The repository does not currently carry a browser automation stack. `tests/Monitor.Web.Tests/Monitor.Web.Tests.csproj` references the .NET test SDK and xUnit only; the current branch contains no Playwright/Selenium/WebApplicationFactory harness. B800 therefore does not introduce a new browser/runtime dependency inside this already broad functional-wiring PR.

This task uses the alternative explicitly allowed by B800-019: document the exact non-browser acceptance boundary and retain the existing production HTTP smoke as runtime evidence.

## Acceptance layers that exist today

### 1. Unit / deterministic projection coverage

`Monitor.Web.Tests` exercises pure diagnostic and recommendation projections, fail-closed evidence handling, collector mapping, authorization metadata, antiforgery metadata and source-level UI/controller contracts.

This proves deterministic application contracts but does **not** execute Razor/JavaScript in a real browser.

### 2. Real SQL acceptance

`.github/workflows/real-sql-acceptance.yml` starts SQL Server 2022, seeds an ephemeral estate, applies `scripts/sql/monitored_sql_least_privilege.sql`, verifies the monitor login is not privileged, builds Release and runs the Real SQL acceptance suite.

This proves the bounded collector and least-privilege SQL contract against a real SQL engine. It does **not** exercise browser rendering.

### 3. Published Windows production-candidate HTTP smoke

`.github/workflows/production-candidate.yml` publishes the Windows x64 candidate, creates ephemeral Production configuration and an ephemeral Administrator credential, starts the exact published application over HTTPS, then runs:

- `scripts/Smoke-Monitor.ps1` for runtime/health behavior;
- `scripts/Smoke-MonitorAuthentication.ps1` for an authenticated session.

The authentication smoke:

1. GETs `/login`;
2. extracts the `__RequestVerificationToken` antiforgery value;
3. POSTs the supplied ephemeral Administrator username/password as form data using the same web session;
4. GETs the protected `/servers/connections` route and requires HTTP 200;
5. runs only against HTTPS, except for an explicit loopback-only opt-in used by local checks.

The Windows workflow then restarts the same published candidate and repeats the smoke. This is meaningful end-to-end HTTP authentication/runtime evidence for the actual published artifact.

## Explicit boundary: what is *not* proved

The current acceptance stack is **not browser automation**. It does not prove:

- DOM layout or visual correctness in Chrome/Edge/Firefox;
- client-side JavaScript interaction semantics;
- responsive breakpoints or pixel-level rendering;
- keyboard/focus/accessibility behavior in a browser engine;
- every role-specific navigation path or every visible button via DOM interaction.

Those dimensions require a separately scoped browser harness (for example Playwright) with explicit dependency, runtime, secret, flake-management and CI ownership decisions. B800-019 does not pretend the current HTTP smoke is equivalent to that harness.

## Safety boundary

- No production environment is contacted by this task.
- No new browser package, downloaded browser binary or external service is introduced.
- The production-candidate smoke continues to use ephemeral credentials and loopback HTTPS.
- This documentation does not publish/supersede RC.61 and does not satisfy `#162 -> #116 -> #111`.

## Completion gate

B800-019 is implementation-complete when this boundary is tracked in the B800 ledger. Exact-head CI/Real-SQL/Windows candidate must still be Green before the encompassing PR can be Ready/merged.
